# vra-vcfa-identity-migration: vRA 8 identity to VCFA

One utility in the `kobi-vcf-utils` repo (see the root `CLAUDE.md` for repo conventions). Run every command and test below from this folder.

Exports users, groups and roles from vRA 8.x and creates the groups, plus the users whose roles are not inherited from a group, with the same roles in a VCF Automation (VCFA) VM Apps org. User-facing docs are in `HOWTO.md`; keep it in sync when options change.

**Two implementations with identical logic and file formats:** PowerShell (`*.ps1`, no dependencies, what customers get) and Python (`*.py`, needs `requests`). The PowerShell version is the primary one. When you change behavior, change both and re-run the parity check (below).

## Identity source step (in progress, PowerShell only)

Why: before groups are loaded into VCFA, the AD groups must be provisioned in the VCF Operations identity source (VCF Identity Broker, "Group Provisioning": base group DNs). `Sync-IdentitySource.ps1` (steps `login`, `extract`) logs in to IDM (Workspace ONE Access / vIDM, e.g. `idm`) and VCF Operations (e.g. `vcf-ops`) and reads the base DNs. Steps: `login`, `extract`, `compare` (read only: IDM's base DNs against VCF Operations' base group DNs). Steps also include `apply -AddBaseDn <dn>`, the ONLY write in the script (everything else, including the two logins, only reads): it adds a select-all base DN entry (`{ baseDn, selectAll: true, compliant: true }`, copied from an existing select-all entry) to the VCF Operations sync profile with `PUT .../sync-profile`. Safeguards, keep them: dry run unless `-Apply` AND a typed `yes` (refused when there is no terminal); only additions, checked before sending and again after reading back with `Test-OnlyAdditions` (every other key and every existing entry must be unchanged); the DN must be an IDM base DN and not already in VCF Operations; the current profile is saved to `sync-profile-backup-<time>.json` first and the planned one to `sync-profile-planned-<time>.json`; exactly one directory must be found; 'add all missing' exists at the user's request (wizard choice 1 "All N ... (recommended)", and `-AddAllMissing`); the domain root base DN is a container, so the plan prints a NOTE that every group under it will be provisioned. The PUT has NOT yet been run against the real lab: its endpoint and body shape come from the vendor's "Update Ldap Sync Profile" operation and the GET shape; if VCF Operations rejects it, capture the request the UI sends when a group is added (Copy as fetch) and match that. Wizard (no parameters, step apply): after reading both systems it lists the IDM base DNs that VCF Operations lacks. Choice 1 is "All N of the base DNs below (recommended)" (only offered when more than one is missing) and Enter selects it; then each single base DN, labelled `a single group` or `a CONTAINER: every group under it`; the last choice is Cancel. Then it asks Dry run (default) or Write. The gates after the pick are what keep it safe: Write needs the typed `yes`, and with no terminal it never writes (the default there is only a dry run). Checked with a throwaway harness (fake IDM and VCF Operations built from the real saved profile; 24 checks incl. Enter then dry run writes nothing, All + write + yes sends one PUT with 44 entries and reads back VERIFIED, no terminal never writes, a non-IDM base DN is refused); that harness is not committed. Test case in progress: the user created the group `CN=my-test-group,OU=ca-vra-users,OU=Test,OU=Users,DC=corp,DC=local` in AD and IDM; expected to appear as a third IDM base DN and be missing in VCF Operations. `login` and `extract` have been run against the real lab by the user: both logins and both reads work. **The write is verified against the real lab (2026-11-05):** the apply step added `my-test-group` to the VCF Operations group provisioning and read-back verified. What it took: the public `PUT .../identity-providers/{idp}/ldap-directories/{id}/sync-profile` validates a different body than its GET returns, so the script sends the planned profile, and on the first 400 whose violations are all `must be null` (the read-only `userAttributeMappings[n].required`) or `must not be blank` (`userAttributeMappings[n].directoryAttributeName`, the unmapped `employeeID`) it drops exactly those and resends once. The trim is checked against the ORIGINAL planned profile (same indexes), and the read-back skips `userAttributeMappings`. A single group is added as the UI does it (`{name, dn, baseDn = own DN, objectGuid from IDM, selectAll:false}`); a container is `{baseDn, selectAll:true}`. The UI itself uses an internal endpoint (`/vcf-operations/rest/ops/internal/vidb/identityproviders/{idp}/ldapdirectories/{id}/syncprofile`, needs `csrf-token` and a session cookie); the script does not use it. Every 400 violation is printed. `fetch.txt` (Copy as fetch) holds a live token and is git-ignored by `*.txt`; delete it. There is no test file for this script on purpose (the user tests it with their own credentials); the helper functions were checked against the saved real extract.

Decisions (user): username and password first, browser token as the fallback; local directories are never read or synced (IDM `LOCAL_DIRECTORY` is skipped, no calls); nested groups are not handled (VCF Operations has "Sync Nested Groups" on in its own settings, the script only records IDM's `excludeNestedGroupMembers`); **the unit is the base DN**, not the individual group. In the lab IDM needs exactly two: `DC=corp,DC=local` and `CN=CloudGroups,OU=Groups,OU=Users,DC=corp,DC=local`; a third entry (`CN=Automation,...`, 0 of 1 selected) is a leftover and is ignored. **Compare at base-DN level only (user decision):** IDM has 2 effective base DNs, VCF Operations has 5 hand-picked ones (`OU=Groups,OU=Users,DC=corp,DC=local`, `OU=AppAccess,OU=Team,DC=corp,DC=local`, `OU=Lab,OU=Users,DC=corp,DC=local`, `CN=RoleCheck-Group,DC=corp,DC=local`, `CN=vcfa-custom,OU=Groups,OU=Users,DC=corp,DC=local`) and the two sets are not similar. Do not compare individual groups: an earlier group-by-group check ("4 of the 8 exported groups are not provisioned") was retracted, it ignored that VCF Operations syncs nested groups so those groups may be covered anyway. What "create if missing" should do at base-DN level is still undecided.

Facts verified against the lab (do not re-guess):
- IDM login: `POST /SAAS/API/1.0/REST/auth/system/login` {username, password, issueToken:true} -> `sessionToken`, sent as `Authorization: HZN <token>`. Directories: `GET /SAAS/jersey/manager/api/connectormanagement/directoryconfigs?includeJitDirectories=true` (vendor Accept type gives 406, use `*/*`). Sync profile: `GET .../directoryconfigs/{id}/syncprofile` with `Accept: */*` (`application/json` gives 406); the local directory has none (404/500).
- IDM sync profile shape: `identityInfo.identityGroupInfo.<base DN> = { numSelected, numTotal, mappedGroupData[] = { selected, mappedGroup{ dn, horizonName, objectGuid, groupBaseDN, source } } }`; also `excludeNestedGroupMembers`, `syncSchedule`, `allGroupsSelectedGroupDns`. Only `selected: true` entries are synced (the first version counted every browsed group: 177 instead of 153).
- VCF Operations login: `POST /suite-api/api/auth/token/acquire` {username, password, authSource?} -> `token`; auth source for SSO users is `VCF SSO` (public list at `GET /suite-api/api/auth/sources`). The Fleet IAM API is under `/suite-api/api/fleet-management/iam/...` (documented on developer.broadcom.com, but that portal is JS-rendered and gives no schemas; the appliance's own `/suite-api/docs/rest/index.html` covers only the classic Suite API, not Fleet IAM).
- VCF Operations records: SSO realm (`ssorealms`) has `idpId`; `GET .../identity-providers/{idpId}` has `provisioningConfig.ldapConfigurations[]` (`ldapConfigurationId`, `ldapBindConfiguration.baseDn` = `DC=corp,DC=local`); `GET .../identity-providers/{idpId}/ldap-directories` items have `ldapConfigurationId`, `vidbDirectoryId`, `numberOfGroups` (41 in the lab), `numberOfUsers`. The `ssoRealmId` equals the UUID in the UI address (`.../sso-domains/domain/<id>/identity-source`).
- VCF Operations sync profile (seen in the lab): `GET .../ldap-directories/{ldapConfigurationId}/sync-profile` returns `{ ldapGroups[], ldapUsers[], includeNestedGroupsAndMembers, syncSchedule (HOURLY), userAttributeMappings[] }`. `ldapGroups[]` entries are either one chosen group `{ dn, name, objectGuid, baseDn, selectAll: false, compliant }` or a whole base DN `{ baseDn, selectAll: true, compliant }` (no dn). The UI's "Base group DN" list is the distinct `baseDn` values (5 in the lab). `ldapUsers[]` are individually chosen users (personal data, not kept in the output). Writing is probably `PUT` on the same sync-profile (read it, change it, put it back whole); confirm with the user's test group before any write.

Env vars (defaults, all optional): `IDM_HOST`, `IDM_USERNAME`, `IDM_PASSWORD`, `IDM_TOKEN`, `IDM_METHOD` (password or token), `VCFOPS_HOST`, `VCFOPS_USERNAME`, `VCFOPS_PASSWORD`, `VCFOPS_AUTHSOURCE`, `VCFOPS_TOKEN`, `VCFOPS_METHOD`. Output `identity-sources.json` holds real group and DN names and the LDAP bind DN (not the password; secrets are stripped); it is ignored by git.

## Conventions

- **HTML reports.** Each run ends with `vra-export-report.html` (export `all`) or `vcfa-load-report.html` (loader: dry run, applied, and a refused apply with mode `blocked`). Builders: `New-ExportReportData`/`build_export_report` and `New-LoadReportData`/`build_load_report`; both languages must produce the SAME JSON (keys, order of rows, wording of attention items) so one template renders both. Rows are sorted ordinally (lower-cased name) to match Python. The template builds the DOM with `textContent` only (never `innerHTML`) and the writer escapes `</` as `<\/`, so names cannot inject markup. A missing template only prints a notice. Reports hold user names: `*-report.html` is git-ignored. Tests: report data in `Test-Export.ps1`/`Test-Import.ps1`/`test_export.py`/`test_load.py`, the real files in `Test-Integration.ps1`. Preview by generating from `vra-export.json` and screenshotting with `msedge --headless=new --screenshot` (give it a timeout; it can hang).
- **PowerShell helper block.** The prompt/HTTP helpers (`Die` through `Invoke-Api`, incl. `Sort-Ordinal`) are identical copies in both `.ps1` files; change both. Scripts are dot-source safe (`Main` only runs when `$MyInvocation.InvocationName -ne '.'`) and `Die` throws, so tests can load them. Tests override functions (`Read-Line`, `Invoke-Api`, `Get-AllVcfa`, ...) after dot-sourcing; `$script:ForceInteractive` forces prompts on or off.
- **PowerShell gotchas learned the hard way** (each one bit during the port): (1) variable names are case-insensitive, so a local `$browserToken` collides with the `-BrowserToken` switch; (2) `$PSBoundParameters` inside a function is the function's, so the script computes `$script:NoFlags` at top level; (3) lists: a function that returns with `return ,$arr` must not be wrapped in `@()` by the caller (double wrapping), so list-returning helpers emit flat and callers wrap in `@()`; `Sort-Ordinal` is the one that returns an array object, call it without `@()`; (4) write `${var}://` not `$var://`; (5) keep the files ASCII-only (5.1 reads BOM-less files as ANSI); (6) 5.1 `Invoke-WebRequest` throws on 4xx, and the error body is often only in `$err.ErrorDetails.Message`; (7) decode responses as UTF-8 from `RawContentStream`, not `.Content`; (8) a string request body is sent as ISO-8859-1 by 5.1, which mangles non-ASCII names and passwords, so `Invoke-Api` sends UTF-8 bytes with `charset=utf-8`; (9) `[Array]::Sort($keys, $items, $comparer)` without explicit `[Array]`/`[IComparer]` casts sorts only the keys, so `Sort-ByKey` casts; (10) `ConvertTo-Json` pads `"key":  "value"` so never string-match JSON text.
- **Scripts stay standalone.** Each runs on its own and imports nothing from the other. The `ask()` and `choose()` prompt helpers are intentionally duplicated in both files; if you change one, change the other.
- **Hosts** go through `normalize_host`/`ask_host` (duplicated in both scripts): bare FQDN in, `https://` added when no scheme, explicit scheme kept, port kept, path/slash dropped, invalid input re-asked.
- **Every input is a prompt with an example.** `ask(label, default, secret, example)` shows `[default]` or `(e.g. example)`; `confirm()` is the yes/no helper. Each config constant has an `e.g.` comment. Only `TIMEOUT` and `API_VERSION` are not prompted. A new input must get a prompt, an example, and a test with a mocked `input`.
- **Interactive by default.** No arguments gives prompts with defaults from env vars or the config constants at the top of each file. Flags skip the matching prompt. When `sys.stdin.isatty()` is false nothing is prompted (tests and automation rely on this; tests patch `sys.stdin.isatty`).
- **Login methods (user decision after testing).** Only the browser session token (`-BrowserToken` / `--browser-token`) and the API token (`-ApiToken` / `--api-token`) are supported for the load. Username/password, a token file and a System-org (provider) token did not work when tested and were removed; do not bring them back without testing. With no flag, a token already in `VCFA_API_TOKEN` / `VCFA_BROWSER_TOKEN` is used (API token first); with neither, the script stops and says what to add. Both flags together are refused. In PowerShell the script parameter `$ApiToken` and the config variable `$script:ApiTokenValue` must stay different names, because script parameters live in script scope and variable names are case-insensitive. The `x-vmware-vcloud-auth-context` header is always the org name.
- **Loader is safe by default.** Dry run unless `--apply` or the wizard's Apply choice, which also requires typing `yes`. Never make a write path that skips this.
- **Default load = groups + users whose roles are not inherited (user decision).** `direct_users`/`Get-DirectUsers` computes, from `roleBindings` and `groups[].members`, the users with at least one org role (compared by `norm_role`) that none of their groups gives them; users with no roles, or only group-given roles, are left to the IdP group claim. Modes: default `free`, `--groups-only` = `none`, `--users` = `all` (every user); naming a user in `--only` forces `all` for that name; `--users` with `--groups-only` is refused. The plan carries `directUsers` and `localUsersWithRoles` (local users with roles are never created, only listed). Project-only users get a synthetic org_member binding in the export, so they count as direct. The export also records `memberOf` per user (informational).
- **Projects are record-only (user decision).** Never add code that writes project membership. The export records projects and `project:*` bindings; the loader only lists them in `plan["projectBindings"]`.
- **Role names** are matched with `norm_role` (case/punctuation-insensitive, Admin == Administrator) and the loader always uses VCFA's own spelling. Bindings in the import keep the original `vraRole`.
- **Role parity.** `build_plan` records roles that do not exist in VCFA per principal (`missingByPrincipal`); `--apply` dies if any planned object is affected unless `--allow-missing-roles`. After apply `verify_roles` re-reads VCFA and compares to the plan. Project bindings are kept per project in `plan["projectBindings"]` (written to `vcfa-plan.json`, also on apply) but not loaded.
- **Browser token input.** A multi-line 'Copy as fetch' pasted into a prompt breaks (only line 1 is read, the rest answers later prompts), so the PowerShell token prompt (`Read-BrowserToken`) reads the clipboard on an empty Enter. `Get-BearerToken`/`bearer_login` accept a raw token, `Bearer <t>`, a quoted token, or a whole fetch/cURL/PowerShell capture, and refuse text with whitespace and no authorization header instead of sending it as a token. Python has no clipboard prompt. The real console paste of a long single-line token is untested.
- **Wizard trigger in `load_vcfa.py`:** the full wizard runs only when `len(sys.argv) == 1`. With any flag, the action is a dry run unless `--apply` or `--login-only`.
- Config that tests patch (`INCLUDE_DOMAINS`, `USERNAME`, `PASSWORD`, `OUTPUT_DIR`, `VCFA_BROWSER_TOKEN`) are module globals. `VRA_HOST` and `VCFA_HOST` are reassigned from prompts inside `main()`.
- When adding an option: add the flag/parameter and the prompt in BOTH implementations, add the scenario to `HOWTO.md`, add unit tests (Python and PowerShell). If it touches HTTP, extend `Test-Integration.ps1`.

## Domain facts worth remembering

- Both a **browser session token** and an **API token** work for the load (tested). An earlier note said API tokens get 403 on create; that did not hold up in testing, so do not restore it without testing again.
- Group membership cannot be migrated (no VCFA API). For SSO (`OAUTH`) groups the IdP decides membership at login; the VCFA group name must match the IdP claim exactly.
- Only groups added to the vRA org with a role are exported. AD-only groups are not.
- Not migrated: project roles (loader skips `project:*` scopes and counts them), local `System Domain` users (need passwords), `migration:admin` (no VCFA role). `saltstack:` and `codestream:` roles are ignored on purpose (`IGNORE_ROLE_PREFIXES`).
- The VCFA write calls need the `x-vmware-vcloud-auth-context` and `x-vmware-vcloud-tenant-context` headers or they return 403.
- vRA project members come from `/iaas/api/projects` as bare usernames in the `email` field (no domain). `build_import` resolves them to UPNs via a directory of all users and group members, adds project-only users to `imp["users"]` with an `org_member` binding, and reports misses in `unresolvedProjectUsers`/`warnings` (optionally resolved with a default domain). The loader still does not apply `project:*` bindings.
- Existing objects are not recreated, but missing vRA roles are added. Roles are never removed.
- `ROLE_MAP` in `export_vra_identity.py` has TODO-confirmed VCFA role names; the loader's dry run prints the names VCFA really has.

## Security

This folder's `.gitignore` excludes `*.json`, `*.txt` and `*-report.html` (the repo root ignores `.claude/`), because exports hold user data and token captures hold live sessions; only `example-*.json` and `examples/` are let through. Never commit credentials or paste tokens into code, chat or logs. Use env vars or the hidden prompts.
